# Реестр задач и бронирование

[Инструкция для команды](../../../docs/eda/team-handoff.md) — основная точка входа.

`registry.json` — воспроизводимый снимок 1148 ID на EDA-100. `historical_review` — 50 прежних разборов с редакторскими связями; `independent_audit` — 50 новых с отдельным аудитом; `not_started` — остальные 1048. Готовность не означает математической экспертизы. `included_in_checkpoint100` — включение в основные частоты (98), `review_required` — два исключения из этих частот. Отсутствие этого флага не отменяет замечаний аудиторов.

`queue_order` и `queue_batch` относятся к замороженной очереди **150 новых**, а не к общему числу обработанных задач. `eligible_for_next_queue=true` означает оставшиеся 100 подготовленных ID, но не разрешение запуска. ID регистрозависимы. `source_issues` содержит дефекты источника. `sources` и `methodology_sha256` фиксируют происхождение снимка и точные инструкции.

Все `reservation_status=unpublished`, `owner=null`: реальных броней ещё нет. `claims.json` — пустой офлайн-зеркальный реестр будущих подтверждённых броней. Его пустота не гарантирует свободные ID на сервере. Авторитет — актуальные GitHub Issues и явное подтверждение координатора. Координатор при синхронизации добавляет записи со следующими полями:

```json
{
  "issue_url": "ссылка на реальную заявку",
  "owner": "GitHub участника",
  "task_ids": ["точные ID"],
  "status": "reserved",
  "confirmed_by": "координатор",
  "confirmed_at_utc": "время UTC",
  "base_commit": "полный SHA",
  "method_version": "fipi-extension-v1.1"
}
```

Состояния: `proposed` → `reserved` → `in_progress` → `submitted` → `accepted`; `released` освобождает незавершённые ID. `reserved`, `in_progress`, `submitted` и `accepted` блокируют пересечения в локальной проверке, в том числе пока снимок готовности ещё не обновлён. `proposed` не бронь, но проверяется координатором на сервере перед подтверждением. Принятые ID включаются в обновлённый реестр готовности. При частичном освобождении разделить списки ID на записи с разными статусами. Пример выше — описание схемы, не реальная бронь.

Из корня репозитория, Python 3 (в Windows можно `.venv/Scripts/python.exe`):

```text
python scripts/fipi_team_registry.py check
python scripts/fipi_team_registry.py check-claim --ids ID1 ID2
```

Заменить ID1/ID2 реальными ID оставшейся очереди. Проверка отклоняет неизвестные/повторные ID, готовые задачи, дефекты источника, ID вне очереди и пересечения с активными локальными бронями. Она не обращается к GitHub и не подтверждает бронь. Перед проверкой получить актуальный зеркальный `claims.json`, затем проверить сервер с координатором.

`python scripts/fipi_team_registry.py build` пересоздаёт **только локальный снимок EDA-100**, не расширяет его новыми результатами и не назначает задачи. При приёмке будущей серии нужна новая версия снимка с новыми входами; не перезаписывать checkpoint-100-v1. Claims живут отдельно и командой build не меняются.
