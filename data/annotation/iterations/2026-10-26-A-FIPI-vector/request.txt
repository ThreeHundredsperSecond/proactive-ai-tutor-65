Ты размечаешь математическую задачу для предметной модели тьютора. Реши задачу самостоятельно по условию. Не обращайся к источникам, ответам и готовым решениям. Не используй инструменты. Верни только JSON, без Markdown.

Общие определения и детализация:
Step — конкретное содержательное математическое действие с проверяемым результатом в данном решении. Выделяй смену математической операции или основания; элементарную арифметику внутри одной операции не дроби. Не добавляй шаги «прочитать условие», «записать ответ». Включи необходимые доказательства, ограничения и проверку полноты, если без них решение не обосновано. Для многопунктной задачи охвати все пункты и обозначь их в action. Не перечисляй неиспользованные альтернативы.
KC — кандидатное переиспользуемое умение, необходимое для действия: name начинается с глагола, description задаёт математическую операцию и условия применения. Не включай в KC числа, имена точек и контекст конкретной задачи. KC не равен теме, конкретному результату или целому методу. Разные формулировки одного умения объединяй внутри задачи; один KC может относиться к нескольким шагам, один шаг — к нескольким KC. Не добавляй умения, которые фактически не применены.
Method — осмысленный способ решения, объединяющий упорядоченные Step для достижения цели или отдельного пункта. Назови стратегию, а не тему и не «решение задачи». Не создавай Method для каждой элементарной операции; не объединяй независимые пункты без общего способа. step_ids отражает порядок применения.
Это кандидаты предметной модели, не доказанные предпосылки освоения и не оценка ученика.

Рамка A-FIPI-v1:
Полный перечень предметных требований дан ниже в FIPI_REQUIREMENTS. Это фиксированные верхние классы, не готовый каталог атомарных KC. Коды и формулировки не изменяй и новые официальные коды не придумывай.
Сначала определи предположительно применимые требования. Самостоятельно реши задачу, не ограничивая способ решения первоначальным выбором, затем уточни выбранные требования по реально выполненным шагам.
Внутри выбранных требований сформулируй конкретные переиспользуемые KC по выполненным действиям. Не подменяй конкретное действие целой формулировкой широкого требования. Не перечисляй остальные понятия выбранного требования, если они не использованы в решении.
Для каждого KC запиши связь с подходящим требованием в fipi_links: requirement_code, kc_ids, anchor (точный непрерывный фрагмент requirement из перечня) и reason (почему выполненное действие соответствует этому фрагменту). Свидетельства применения KC находятся в steps.kc_ids. Один KC может иметь несколько обоснованных связей.
Если уверенной связи нет, сохрани её с requirement_code=null, anchor="" и конкретной причиной. Не удаляй нужное математическое действие, чтобы подогнать его под каталог.
В selected_requirements перечисли только коды фактически обоснованных требований. Само наличие общей арифметики не требует добавления всех широких классов: обосновывай выбор существенным действием. Это классификация проекта по официальной рамке, а не официальная разметка ФИПИ.

Верни только JSON строго с этими полями:
{"task_id": "...", "selected_requirements": ["код из перечня"], "solution_status": "solved|partial|unsolved", "steps": [{"id": "s1", "action": "...", "result": "...", "kc_ids": ["k1"]}], "kc_candidates": [{"id": "k1", "name": "...", "description": "..."}], "methods": [{"id": "m1", "name": "...", "step_ids": ["s1"]}], "fipi_links": [{"requirement_code": "код из перечня или null", "kc_ids": ["k1"], "anchor": "точный фрагмент требования", "reason": "..."}], "warnings": []}
Все id уникальны внутри типа; ссылки должны существовать. Все KC применены в шагах и отражены в fipi_links. Неиспользованных KC и пустых методов нет. Допустимые solution_status: solved, partial, unsolved. Необоснованные места отмечай в warnings.
