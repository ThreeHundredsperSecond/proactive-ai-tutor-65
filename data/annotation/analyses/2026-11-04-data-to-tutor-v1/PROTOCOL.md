# От сохранённой разметки к материалам тьютора: протокол v1

**Проект протокола для обсуждения, 4 ноября 2026. Исследование ещё не выполнено.**
Этот документ фиксирует следующий ограниченный анализ перед отдельным запуском. Он не утверждает педагогическую политику и не запускает задачи 101–200. Используем только то, что уже наблюдается в условиях, сохранённых решениях и назначениях KC.

## Вопрос и ожидаемый результат

Что имеющиеся материалы позволяют предложить для подбора упражнений и представления решения по шагам, и каких связей для этого не хватает?

Результат — три небольших читаемых представления с ID, названиями действий, легендами, точными знаменателями и ссылками на свидетельства. Вычисления Python воспроизводимы. Связи из редакторских и независимых аудиторских назначений показываются отдельно. Не получаем из этих данных диагноз ученика, освоение, эффективность подсказки или prerequisite.

## Входы и фиксация версии

- Банк `data/fipi/2026-10-31-profile/tasks.jsonl` и файлы условий/изображений из его каталога.
- Пилот `data/annotation/runs/2026-10-31-fipi-50x1/`: manifest, raw, review-decisions и catalog-decisions.
- Расширение `data/annotation/runs/2026-11-02-fipi-extension-150/`: первые 50 ID очереди, замороженный каталог и активные попытки из `active-scopes/first-050-603ec8fe8e05fe2d.json`. Наличие остальных ID в очереди не означает их обработку.
- Политика включения и определения метрик из [зафиксированного EDA-100](fipi-100-checkpoint.md); его основные частоты — по 49+49 задачам, состав — по 50+50. Исключённые задачи сохраняются отдельно с причинами.

При начале записать Git SHA, хеши всех прочитанных входов и использованного кода, версии Python/пакетов, точные выбранные ID, параметры отбора, время запуска. Использовать read-only сбор входов с закреплённым active manifest; не вызывать исторические команды, которые перезаписывают derived. Сверить исходные частоты с EDA-100 до построения новых графиков. Таблицы исполненного предварительного ноутбука можно использовать как контроль, но не вместо исходных свидетельств.

## 1. Какие задачи связаны общим действием

**Метод.** Двудольный граф «задача ↔ узел каталога KC». Ребро существует только при сохранённом редакторском назначении в пилоте либо принятом неблокирующем `match` независимого аудитора в расширении. Дедупликация по паре ID задачи и ID каталога. Пропущенные связи не достраивать по похожим названиям, предложения `needs_split` не превращать автоматически в назначения.

**Метрики.** Для KC: число разных задач с принятой связью по каждому слою; число разных первых КЭС среди этих задач; распределение форматов ответа; список всех меток КЭС отдельной таблицей. Множественные метки не суммировать как доли независимых задач. Разнообразие КЭС — описание метаданных источника, не доказательство разных учебных контекстов или переносимости навыка. Термин «контекст» в графике сопровождается буквальным условием/меткой, без новой классификации агентом.

**Отбор фрагментов.** Первый фокус — `linear_equation` (проверить существование ID и число назначений при запуске). Ещё максимум два узла: не меньше трёх включённых задач, хотя бы одно назначение в каждом слое; порядок по числу задач, затем по строковому ID. Если подходящих нет — не ослаблять правило молча. Сохранить полные списки ID. Для рисунка не более 12 задач на узел: поровну из двух слоёв, при нехватке заполнить из другого; внутри слоя отбирать по одному из сочетаний «первый КЭС × формат», далее в порядке ID. Полные метрики всегда по всем задачам узла, а не только показанным.

**Читаемый выход.** Небольшой граф с русским названием действия, ID задач, цветом по слою и меткой КЭС/формата; рядом карточки с фрагментами условий, ссылкой на полное условие и цитатой шага. Внешние метки ФИПИ отделить от названия KC. Использовать фиксированные координаты или seed раскладки, без общей «паутины» всех узлов. Сохранить PNG и HTML с локальными ссылками. Вывод ограничить: какие конкретные задания являются кандидатами для практики одного принятого действия; предметный допуск ещё не установлен.

## 2. Какие последовательности наблюдаются в решениях

**Метод.** Для задач первого фокуса построить цепочки **сохранённых шагов** внутри каждого Method: текст действия → результат → назначенные KC. Сохранить step ID, ссылки на входное состояние и происхождение. Если шаг не имеет полного назначения, оставить его в цепочке явно неназначенным; не соединять соседние принятые KC через пропущенный шаг. Несколько KC в одном шаге показать группой без внутреннего порядка. Независимые пункты и альтернативные методы не склеивать.

**Метрики.** Число задач с принятым KC в предыдущем/следующем соседнем шаге в рамках Method, без повторного счёта одной задачи для одной направленной пары. Отдельно — число фокусных задач, где соседний шаг есть, но содержит неназначенные кандидаты. Если пара наблюдается только в одном случае, показывать «1 задача», не именовать её устойчивым маршрутом. Отсутствие наблюдаемого перехода не означает невозможность другого правильного метода.

**Выход.** До четырёх схем решения: сначала одна исходная и одна новая задача, затем до двух новых с неполными назначениями; выбирать в порядке ID, не повторяя уже взятые задачи. Если категории пусты — указать отсутствие, не подбирать удобный пример за пределами фокуса. Полная таблица цепочек сохраняется. Это основание предложить, какие действия можно явно наблюдать в будущем интерфейсе; вопросы ученику и правила реакции пока не генерируются.

## 3. Где разметки недостаточно для использования материалов

**Метод.** Профиль полноты сохранённых связей, а не новая оценка математической правильности. Сопоставить только уже существующие признаки: source_issues, статус решения, блокирующие замечания, режим получения активной попытки, число кандидатов без полного назначения. Явно показывать происхождение: полнота исторических редакторских назначений не сопоставима с независимым аудитом как оценка качества.

**Метрики по слоям.** Число задач со всеми/частью/ни одним назначенным кандидатом среди включённых задач; количество неназначенных кандидатов по статусам аудитора; число исключённых задач и сохранённые причины. Категории source issues/feedback/blocking могут пересекаться, поэтому не складывать их в один «процент качества». Число полностью сопоставленных задач не называть числом проверенных учебных эталонов.

**Выход.** Небольшая таблица или диаграмма полноты по слоям и панель нескольких уже сохранённых причин: составной кандидат, перекрытие определений, ошибка чтения, спорное допущение. Отобрать по одному существующему примеру из EDA-100, подписать как иллюстрации, не выборку распространённости причин. Новые смысловые категории на весь корпус не размечать. Вывод: что можно использовать как материал проектирования, где нужно уточнение каталога, где требуется предметная проверка; готовность оценивать ученика не устанавливается.

## Выполнение и health checks

1. Подготовить read-only загрузку и manifest; сверить состав 100 ID, знаменатели 49/49/98 и частоты с зафиксированным отчётом.
2. Построить **один фокус**. Проверить минимум три показанные задачи: исходную, новую с принятой связью и новую с неполным сопоставлением, если такие есть в фокусе. Проверить цитаты, назначенные ID, изображения и отсутствие выдуманных рёбер. Если категория отсутствует, записать это в журнале и проверить другой тип отдельно без включения его в фокусные метрики.
3. Просмотреть картинку и схемы: подписи читаемы без знания нашей переписки, легенда объясняет происхождение и отбор, ссылки ведут к исходному материалу. Сохранить проверенные ID, расхождения и исправления кода. Это технический/выборочный просмотр, не независимая экспертиза.
4. Только после успешной проверки первого фокуса построить ещё максимум два по зафиксированному правилу и сводку полноты. При несовпадении хешей/контрольных частот, неверном ребре или нечитаемом представлении остановиться, исправить причину и повторить проверку.
5. Исполнить отдельный ноутбук с нуля, сверить CSV/метрики повторного запуска и проверить сохранность исторических входов. Остановиться и показать результат пользователю; не переходить автоматически к созданию тьютора.

## Что сохраняется и как повторить

Новый отдельный каталог `data/annotation/analyses/<дата>-data-to-tutor-v1/`: `PROTOCOL.md` (копия этой версии), `manifest.json`, `report.md`, исполненный `review.ipynb`, `figures/`, `tables/`, `cards/`, `checks/`, `provenance.json`, `output-hashes.json`. Код — отдельный `scripts/analyze_data_to_tutor.py`, будущая команда запуска и зависимости описываются в README результата. Старые каталоги и итоговый предварительный EDA не перезаписывать.

Manifest хранит полные и показанные наборы ID, исключения и причины, KC-фокусы и правила, seed раскладки при его наличии. CSV сохраняют рёбра с источником, цепочки с step/Method ID, показатели с явными знаменателями и неотображённые записи. HTML-карточки сохраняют MathML/изображения и ссылки на raw/аудит. Новые модельные ответы, промпты, синтетические ученики, смысловая переклассификация и независимый агентный аудит в этом этапе **не требуются и не запускаются**.

Из данных нельзя вывести, какую подсказку давать, как обновлять освоение, сколько повторов достаточно и какова эффективность обучения. Эти вопросы остаются отдельным этапом проектирования и испытаний.
