## Текущий фокус и продолжение работы

Рабочая ветка — `docs/full-ege-math-scope`. Новые ветки, commit/push и слияние в main — только по поручению пользователя.

Единая точка чтения и сдачи — [notebooks/checkpoint-2/EDA.ipynb](notebooks/checkpoint-2/EDA.ipynb). Читает сохранённый банк и 100 разборов; основные частоты по 98. Новых генераций не запускать. Смысловые интерпретации и каталог предварительные, не экспертный эталон и не профиль ученика. PDF практической ценности пока предварительный, обновляется отдельно.

6 ноября по поручению пользователя выполнена локальная реорганизация для проверки: архивные ноутбуки, пилот и черновики перенесены; данные не меняются. [Дерево и переносы](docs/repository-layout.md), [история решений](docs/research-history.md), [полный прежний журнал](research/archive/project-log.md). Архивные снимки сохраняются побитово, [карта путей](docs/archive-paths.json) и [указатель ссылок](research/archive/link-index.md) обеспечивают прослеживаемость старых записей.

Текущий пересчёт: `scripts/build_checkpoint2.py`, затем `scripts/verify_checkpoint2.py`. `scripts/archive_support.py` разрешает прежние пути при проверке замороженных входов, не переписывая манифесты. Старые ноутбуки и команды — исторические снимки; для сдачи используется только текущий EDA. Реорганизация не разрешает повторные модельные прогоны или переподготовку старых наборов.

Командная работа — [docs/eda/team-handoff.md](docs/eda/team-handoff.md), [старт агенту](docs/eda/team-agent-start.md), реестр `data/annotation/team/registry.json`. До новой обработки нужны подтверждённые координатором ID, объём и остановка. Старые 50/100, исходные ответы/каталоги и реестр не менять.

Исторические указания о других ветках и незавершённых этапах находятся в архивном журнале и не отменяют эту точку продолжения. Связные причины и результаты описаны в истории исследования; при отсутствии свидетельства не придумывай задним числом мотив решения.

## Структура и ведение EDA

- Три уровня: `docs/eda/README.md` — общий маршрут и сводный статус; `docs/eda/<этап>/README.md` — цель, прогресс и продолжение; отдельные файлы внутри этапа — материалы и результаты.
- После работы обновляй README соответствующего этапа: что сделано и где результат, что узнали, открытые вопросы, место остановки и следующее конкретное действие. Общий README обновляй только в части краткого статуса и навигации.
- Не дублируй подробные результаты между уровнями. Ссылка или план будущего файла не означает, что он уже создан. Не помечай этап выполненным только потому, что подготовлен план.
- Последовательность: официальная карта ФИПИ → задачи → проверенные решения → содержательные шаги → навыки. Тема ФИПИ и навык — разные сущности; сохраняй официальные коды и формулировки отдельно от последующей разметки проекта.
- При переносе прочитанного пользователем материала сохраняй содержание; исправляй пути ссылок. Отмечай факт пользовательского просмотра и его версию в README этапа. При последующих содержательных изменениях явно перечисляй изменённые разделы для повторного просмотра; не переноси статус проверки автоматически на новый текст.
- Старые пути `docs/eda-plan.md` и `docs/fipi-overview.md` — указатели для совместимости, не места для новой работы. Изображения ФИПИ остаются в `docs/images/fipi-2027/`.

## Работа с концепцией и документами

- Различай принятые решения, рабочие гипотезы, предложения и открытые вопросы. Не объявляй черновик согласованным с командой или куратором без основания.
- Концептуальные изменения вноси в `docs/project-vision.md`; годовые сроки и задачи — в `docs/project-plan.md`; текущую работу с данными — в `docs/eda/README.md`; подробные вопросы — в `docs/tutor-design-questions.md`; обзоры исследований — в `research/`.
- В README сохраняй краткую навигацию. Обновляй ссылки при добавлении или переименовании документов.
- Не выбирай за команду окончательную архитектуру, модель, базу данных или формат интерфейса при задаче на документацию.
- При противоречии документов явно обозначь его; не подменяй согласование молчаливой переработкой плана.
- Пиши по-русски, кратко и конкретно; технические идентификаторы сохраняй в исходном виде.
- В документах для читателя (README, обзоры, история исследования, отчёты, EDA и PDF) описывай проект, методы, результаты, ограничения и открытые вопросы. Не вставляй служебные заметки о разрешениях пользователя, ожидании его просмотра, запретах на автоматическое продолжение, commit/push или внутренних действиях агента. Такие инструкции храни в AGENTS.md и специально предназначенных агентам инструкциях; текущий статус локальной работы сообщай в чате. Содержательные ограничения и происхождение данных сохраняй. При редактировании генерируемого документа исправляй также источник генерации, чтобы служебный текст не вернулся после пересборки.
- Не веди обзорные README как журнал диалога с пользователем: давай актуальное состояние и ссылки на датированные эксперименты. Правила командной координации оставляй в инструкции участникам, а замороженные промпты и архивные журналы сохраняй как первичные свидетельства.

## Предметная модель и данные

- Различай официальное предметное требование ФИПИ, тему, KC, метод решения и конкретную задачу. Коды требований и содержания независимы; связывай их только по явно указанным данным ФИПИ. KC описывай через действие; метод связывай с последовательностью содержательных шагов.
- Извлечение KC из задач и co-occurrence — рабочая гипотеза. Статистика даёт кандидатов на методы, но не доказывает смысл, порядок или зависимости.
- Сохраняй связь задачи, решения, шага, KC и источника; фиксируй версию экзамена отдельно от навыка.
- Математическую корректность решений и разметки проверяй. Не представляй генерацию LLM как предметную валидацию.
- Различай самостоятельное решение и решение с подсказкой. Не считай показ объяснения свидетельством освоения.
- Для внешних материалов фиксируй источник и условия использования; проверочный набор отделяй от примеров разработки.
- Не переноси данные, исторические метрики или устройство Anki-проекта как уже реализованные компоненты этого тьютора.

## Git и проверка изменений

- Перед изменениями проверь корень репозитория, текущую ветку и состояние рабочего дерева. Сохраняй чужие незакоммиченные изменения.
- Работай в согласованной ветке `docs/full-ege-math-scope`. Не создавай новую ветку без поручения пользователя.
- Без явного поручения не вноси изменения напрямую в `main`, не сливай ветки и не включай автоматическое слияние. Не переписывай чужую историю.
- Ограничивай изменения порученной задачей. Для документации проверь diff, относительные ссылки, структуру Markdown и схемы; для кода запускай проверки, соответствующие изменению.
- Не коммить секреты, персональные данные учеников и локальные материалы без оснований для их публикации.
- В отчёте кратко укажи изменённые файлы, ветку, выполненные проверки и ограничения. Не утверждай, что push, тесты или слияние выполнены, если они не выполнены.

## Формулы в GitHub Markdown

- Для формул внутри строки используй `$...$`, для отдельной формулы — блок ```math` (с закрывающими тройными обратными кавычками). Не используй `\\(...\\)` и `\\[...\\]` в файлах GitHub Markdown.
- Не используй одиночные `$` на отдельных строках для блочных формул. Пример:

````markdown
```math
J(A,B)=\\frac{|A\\cap B|}{|A\\cup B|}
```
````

- После записи прочитай фактическое содержимое файла из GitHub и проверь точное число знаков `$`, обратных слэшей и ограждений блоков. Перед редактированием согласованного текста показывай предлагаемые изменения и меняй только одобренное.
